Documentacao Tecnica — Modulo Seller

Versao: 1.1.0 | Release: Seller v1.1 Stack: ADVPL sobre TOTVS Protheus Autor: Jose Antonio

1. Visao Geral​

O modulo Seller e responsavel pela integracao de Notas Fiscais de Venda e Devolucao entre o ERP Protheus e o sistema externo Campos Dealer. O fluxo consiste em extrair notas pendentes, transforma-las em payloads JSON, envia-las via REST e auditar cada operacao na tabela ZRM.

1.1 Componentes (8 arquivos PRW)​

sellCfg.prwConfiguracao, ambiente RPC, credenciais, MVsSHCFG
sellQry.prwExtracao de notas via SQL (anti-join ZRM)SHQRY
sellBld.prwTransformacao: agrupamento e construcao JSONSHBLD

AtributoValor
ArquivosellMain.prw:625

Descricao: Funcao MAIN de Schedule. Executa ambos os fluxos em sequencia: primeiro vendas (U_SHSELL01), depois devolucoes (U_SHSELL02).

Tratamento defensivo de parametros:

  2. Se falhar, tenta fallback para cEmpAnt/cFilAnt (ambiente ja aberto).

  4. Abre RPC apenas se cEmpAnt nao existir; fecha apenas se abriu.

Fluxo interno: SHSELL05 → U_SHSELL01 (vendas) → U_SHSELL02 (devolucoes)

3.9 SHSELL09 — Fachada do Sender REST​

AtributoValor
ArquivosellSnd.prw:5
ParametroscOper (C), aParams (A)
RetornoVariant
ChamadaU_SHSELL09(cOper, aParams)

Descricao: Fachada publica do componente de envio REST. Suporta 2 operacoes:

OperacaoStatic chamadaParametrosRetorno
"SEND"SHSENDENV0{oPayload, oCred}Array {nStatus, cResposta, lSucesso}
"POSTUPDATE"SHSENDPOS0{oCred}Logical

Detalhes do SEND:

  • Endpoint: /PRTNotaVenda/grupo/{IdGrupo}/empresa/{idFilial}/CreateNotaVenda
  • Autenticacao: Authorization: Basic {Token}
  • Retry: ate ES_SELLRETR tentativas (default 3).
  • HTTP 200-299: sucesso. HTTP 409: sucesso funcional (nota ja cadastrada).
  • HTTP 400: erro irrecuperavel — interrompe retry.
  • Fallback textual: detecta "NOTA" + "CADASTRADA" na resposta mesmo se oRest:Post() falhar.
  • Usa HTTPGetStatus(@cError) e DecodeUTF8() para tratamento da resposta.

Detalhes do POSTUPDATE:

  • Endpoint: /PRTNotaVenda/grupo/{IdGrupo}/PostAtualizaNotaVenda
  • Notifica o CRM para processar recebimentos apos integracao.

10. Tratamento de Erros​

10.1 Orquestrador (sellMain)​

  • Begin Sequence / Recover Using oErro em dois niveis: nota individual e filial.
  • Erro em nota: loga via ConOut, continua processando proximas notas.
  • Erro em filial: loga e encerra fluxo daquela filial.
  • Objeto de erro inspecionado para ValType == "J" vs "O" com fallback para Description/description.
  • Alias de query sempre fechado no final, mesmo em caso de erro (If !Empty(cAlias)).

10.2 Sender REST (sellSnd)​

  • Retry loop com maximo ES_SELLRETR tentativas.
  • HTTP 400: interrompe imediatamente (erro de schema/validacao).
  • HTTP 409: tratado como sucesso (nota ja existe).
  • Fallback textual: detecta "NOTA" + "CADASTRADA" na resposta mesmo se oRest:Post() falhar.
  • DecodeUTF8() com code page cp1252 para caracteres acentuados.

10.3 Logger (sellLog)​

  • RecLock("ZRM", .T.) — lock otimista; se falhar, operacao e ignorada silenciosamente.
  • FieldPos() protege campos customizados — se o campo nao existir no ambiente, a atribuicao e ignorada.

10.4 Query (sellQry)​

  • Validacao de todos os parametros antes da montagem SQL (ValType, Empty, AllTrim).
  • StrTran(..., "'", "''") em todos os valores concatenados na SQL (protecao contra SQL injection).
  • TCSetField para fixar tipo Date no campo EMISSAO.
  • ConOut de diagnostico com dados de contexto em caso de falha.
